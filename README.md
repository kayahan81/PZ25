# Отчёт
1.	Какие ключи кэша используются и как они формируются.
Используются два типа ключей:
- tasks:task:{id} — для кэширования отдельной задачи, где {id} заменяется на конкретный ID задачи
- tasks:list — для кэширования всего списка задач

Ключи формируются методами GetTaskKey(id) и GetListKey() в RedisCache. Такой подход обеспечивает уникальность ключей для каждой сущности и простую инвалидацию.
2.	Как реализован cache-aside (описание алгоритма).
Реализована стратегия cache-aside (ленивая загрузка):
- При запросе GET /tasks/{id} сначала пытаемся прочитать из Redis по ключу
- При попадании (hit) — десериализуем JSON и возвращаем данные
- При промахе (miss) или ошибке Redis — идём в БД через репозиторий
- После получения данных из БД асинхронно сохраняем их в Redis с TTL
- При недоступности Redis сервис продолжает работать через БД
3.	Какие TTL и jitter использованы и почему.
Базовый TTL = 120 секунд (2 минуты)
Jitter = 0-30 секунд (случайный разброс)
Итоговый TTL = 120 + rand(0..30) секунд
Jitter используется для предотвращения cache avalanche — ситуации, когда множество ключей истекают одновременно, вызывая всплеск нагрузки на БД. Случайный разброс распределяет истечение кэша во времени.
4.	Как выполняется инвалидация при update/delete.
При операциях изменения (PATCH, DELETE):
Немедленно удаляется ключ конкретной задачи tasks:task:{id}
Также удаляется ключ списка tasks:list
Удаление выполняется асинхронно (через goroutine) с timeout 1 секунда
При ошибке удаления только логируем предупреждение, но не прерываем операцию
5.	Как реализована деградация при недоступности Redis.
Деградация реализована на нескольких уровнях:
- При инициализации: если Redis недоступен, кэш создаётся, но client = nil
- При операциях Get/Set/Delete: проверка if r.client == nil { return nil }
- Таймауты на операциях Redis (ReadTimeout/WriteTimeout = 500ms)
- При ошибках Redis: логируем WARN и идём в БД (graceful degradation)
- Сервис продолжает работать, теряя только ускоряющую функцию кэша

# Ответы на вопросы
1.	Что такое cache-aside и почему он часто используется?
Это стратегия, где приложение сначала проверяет кэш, и только при промахе обращается к БД, после чего сохраняет данные в кэш. Она часто используется, потому что проста в реализации, даёт полный контроль над кэшированием и позволяет кэшировать только реально запрашиваемые данные.
2.	Зачем нужен TTL?
TTL нужен для автоматического истечения кэша, чтобы данные не хранились бесконечно и могли "самообновляться" со временем. Это предотвращает использование устаревших данных и контролирует размер кэша.
3.	Что такое cache avalanche и как jitter помогает?
Cache avalanche — это ситуация, когда множество ключей кэша истекают одновременно, вызывая резкий всплеск запросов к БД. Jitter (случайный разброс TTL) помогает, распределяя моменты истечения ключей во времени, что сглаживает пиковую нагрузку на БД.
4.	Почему Redis не должен быть “источником истины”?
Данные могут быть потеряны при перезапуске, сброшены по TTL или при нехватке памяти. Источником истины должна быть БД с persistent storage и транзакционной поддержкой.
5.	Как правильно вести себя сервису при падении Redis?
Сервис должен деградировать gracefully: логировать ошибку как WARN/ERROR, но продолжать обслуживать запросы через прямое обращение к БД. Redis является ускорителем, а не критической зависимостью, поэтому его недоступность не должна приводить к отказу сервиса
